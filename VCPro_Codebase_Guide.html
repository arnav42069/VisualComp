1. Project Overview

Visual Comp Pro is a professional-grade audio compressor plug-in built with the JUCE C++ framework. It loads inside a Digital Audio Workstation (DAW) such as Ableton Live, Logic Pro, or FL Studio.

What it does for the listener

  • Reduces the dynamic range of audio — loud parts get quieter so quiet parts feel louder.
  • Adds analogue character through four vintage-modelled circuit types (VCA, FET, Optical, Tube).
  • Provides rich real-time visuals: dual oscilloscope, VU needle meter, and a live transfer-curve graph.

The JUCE plugin entry point

At the very bottom of PluginProcessor.cpp is this one-liner that every JUCE plugin must have:

juce::AudioProcessor* JUCE_CALLTYPE createPluginFilter() {
    return new VisualCompProcessor();  // the DAW calls this to make your plugin
}

The DAW loads your DLL/VST3/AU, finds this symbol, calls it, and receives your processor object.

3. Threading Model

This is the most important concept in audio plugin programming. The DAW runs two separate threads that must never block each other.

ThreadWho runs itWhat happens hereRule
Audio Thread DAW / OS audio driver processBlock() — runs every ~5 ms at 44100 Hz No allocation, no locks, no GUI calls
Message Thread JUCE message loop All GUI painting, timer callbacks, user input No blocking, no direct audio buffer access

How this plugin crosses the thread boundary safely

AUDIO THREAD MESSAGE THREAD ───────────── ────────────── processBlock() Timer::timerCallback() (every 8–33 ms) │ │ │ writes atomically │ reads atomically ▼ ▼ gainReductionDb (std::atomic<float>) ──► VuMeter reads needle target currentInputLevelDb (atomic) ──► GrCurveDisplay shows live dot │ │ │ lock-free ring-buffer push │ lock-free ring-buffer read ▼ ▼ WaveformBuffer::push() WaveformDisplay::timerCallback() (writes writePos last) (reads writePos first — acquire fence)

std::atomic operations and the acquire/release memory ordering on writePos are the only synchronisation primitives used. There are no mutexes, which means the audio thread can never stall waiting for the GUI.

Why no mutex? If a mutex is held by the GUI thread when the audio thread needs it, the audio thread blocks. Even a 1 ms block causes an audible dropout. std::atomic operations are wait-free and never cause stalls.

WaveformBuffer struct (lines 8–24)

struct WaveformBuffer {
    static constexpr int size = 65536;         // must be a power of 2!
    std::array<float, size> data {};
    std::atomic<int> writePos { 0 };

    void push(const float* samples, int numSamples) noexcept {
        int pos = writePos.load(memory_order_relaxed);
        for (int i = 0; i < numSamples; ++i) {
            data[pos] = samples[i];
            pos = (pos + 1) & (size - 1);  // power-of-2 modulo: wrap around
        }
        writePos.store(pos, memory_order_relaxed);
    }
};
  • Ring buffer / circular buffer: a fixed-size array where the write pointer wraps around to the start when it reaches the end. This gives you a rolling window of the most recent 65,536 samples (~1.5 seconds at 44.1 kHz) without ever allocating memory.
  • Power-of-2 size trick: (pos + 1) & (size - 1) is a fast modulo operation that only works when size is a power of 2 (65536 = 2¹⁶). It replaces the slower % size.
  • noexcept: guarantees the function never throws an exception. Required for anything called on the audio thread.

5. PluginProcessor.cpp — Audio DSP Line by Line

PluginProcessor.cpp All audio processing — the heart of the plugin

Saturation helper functions (lines 4–22)

fastTanh(x) — line 4

static inline float fastTanh(float x) noexcept {
    const float x2 = x * x;
    return x * (27.0f + x2) / (27.0f + 9.0f * x2);
}

A rational polynomial approximation of tanh(x) that is faster than the std::tanh library function. tanh is used as a soft-clipping function — it smoothly rounds off the peaks of audio without the harshness of hard clipping. The approximation error is under 0.5% across the audio range.

fetSaturate(x, drive) — line 10

static inline float fetSaturate(float x, float drive) noexcept {
    const float k       = 1.0f + drive * 2.2f;
    const float clipped = fastTanh(x * k) / k;        // symmetric soft clip
    const float asym    = drive * 0.018f * clipped * std::abs(clipped); // even-harmonic bias
    return clipped + asym;
}

Models an FET (Field-Effect Transistor) input stage. The asym term adds even-order harmonics (2nd, 4th…), giving the characteristic "punchy" tone of an 1176-style compressor. More drive = more saturation.

tubeSaturate(x, drive) — line 18

static inline float tubeSaturate(float x, float drive) noexcept {
    const float k   = 1.0f + drive * 1.6f;
    const float sat = std::tanh(x * k) / k;         // smooth symmetry
    return sat + drive * 0.025f * sat * sat;         // even-harmonic glow
}

Models a vacuum tube triode. Uses the standard std::tanh (slightly slower but tube DSP is applied less per sample than FET, so it's fine). The sat * sat term adds warm 2nd-harmonic distortion — the "glow" of tube gear.

createParameterLayout() — lines 36–67

Registers all 9 automatable parameters with JUCE's AudioProcessorValueTreeState (APVTS). Each parameter gets:

processBlock() — lines 96–286 — The Core DSP

This is called by the DAW for every block of audio (~128–512 samples). Here is what happens in order:

Step 1 — Read parameters (lines 104–112)

const float mixAmt      = apvts.getRawParameterValue("mix")->load();
const float attackMs    = apvts.getRawParameterValue("attack")->load();
// … etc for all 9 params

getRawParameterValue() returns a pointer to a std::atomic<float> that JUCE updates whenever the user moves a knob or the DAW sends automation. Calling .load() is a thread-safe read — no locking needed.

Step 2 — Mode-specific time constant clamping (lines 121–138)

switch (mode) {
    case FET:     effAttack  = jmin(attackMs, 2.0f);   // FET is ultra-fast
                  effRelease = jmax(releaseMs, 20.0f);
    case Optical: effAttack  = jmax(attackMs, 30.0f);  // Optical is programme-dependent
                  effRelease = jmax(releaseMs, 100.0f);
    case Tube:    effAttack  = jmax(attackMs, 50.0f);  // Tube is inherently slow
                  effRelease = jmax(releaseMs, 200.0f);
}

Each hardware compressor type has a characteristic speed range. This enforces those ranges so that, for example, you can't accidentally make an Optical compressor act like a limiter (which would be unrealistic).

Step 3 — Compute attack / release coefficients (lines 140–141)

const float attackCoeff  = std::exp(-1.0f / (sampleRate * attackMs  * 0.001f));
const float releaseCoeff = std::exp(-1.0f / (sampleRate * releaseMs * 0.001f));
Why exp()? Envelope followers use a one-pole IIR (infinite impulse response) filter: env = coeff * env + (1 - coeff) * target. The coefficient is derived from the RC time constant formula where τ = attack_seconds and coeff = e^(−1/τ·fs). A coefficient close to 1.0 = slow response; close to 0.0 = fast response. At 44100 Hz with a 10 ms attack: coeff = e^(−1/(441)) ≈ 0.9977.

Step 4 — Save dry buffer for parallel mix (lines 146–151)

if (mixAmt < 0.9999f) {
    dryBuffer.setSize(numChannels, numSamples, false, false, true); // keep existing data
    for (int ch …) dryBuffer.copyFrom(ch, 0, buffer …);
}

Only saves a copy of the input signal when mix is less than 100%. The 0.9999f threshold avoids the copy when it's not needed (saves CPU).

Step 5 — Push input to oscilloscope buffer (lines 153–158)

monoMixBuffer.clear();
for (int ch …) monoMixBuffer.addFrom(0, 0, buffer, ch, 0, numSamples, inScale);
inputWaveform.push(monoMixBuffer.getReadPointer(0), numSamples);

Mixes all channels to mono (averaging), scales by input gain, and pushes to the inputWaveform ring buffer so the oscilloscope can display it.

Step 6 — Per-sample processing loop (lines 165–265)

This is the innermost loop — it processes every single sample individually:

  1. Apply input gain + saturation (FET/Tube modes add harmonic colour here)
  2. Compute peak level from all channels (or sidechain)
  3. Convert peak to dBFS for comparison against threshold
  4. Compute raw gain reduction using threshold/ratio/knee formula
  5. Smooth GR through the mode-specific envelope follower
  6. Apply smoothed GR + output gain to all channels
  7. Apply limiter / output saturation if enabled

Step 6a — Gain reduction computation (lines 196–210)

if (kneeDb > 0.0f && detDb >= thresh - halfKnee && detDb <= thresh + halfKnee) {
    // Soft knee — quadratic interpolation in the knee region
    const float x = detDb - thresh + halfKnee;
    grDb = x * x * (1.0f / ratio - 1.0f) / (2.0f * kneeDb);
} else if (detDb > thresh + halfKnee) {
    // Above threshold — standard compression formula
    grDb = thresh + (detDb - thresh) / ratio - detDb;
} else {
    grDb = 0.0f;  // below threshold — no compression
}
The compression formula explained: When signal detDb is above threshold:
output_dB = threshold + (input_dB − threshold) / ratio
Gain reduction = output_dB − input_dB = threshold + (input_dB − threshold)/ratio − input_dB
At ratio 4:1 with threshold −20 dB and input −10 dB:
GR = −20 + (−10 − (−20))/4 − (−10) = −20 + 2.5 + 10 = −7.5 dB

Step 6b — Envelope follower per mode (lines 212–240)

ModeEnvelope behaviourHardware it models
VCA Classic one-pole IIR: attack coeff when GR is increasing, release coeff when recovering SSL 4000G, API 2500, dbx 160
FET Same as VCA but clamped to ultra-fast attack (≤ 2 ms) — very aggressive Urei 1176, Purple MC77
Optical Maintains a separate opticalState (0–1) representing the photocell brightness. GR = -opticalState × 20 dB × (1 + opticalState × 0.5) — non-linear release that gets slower as the compressor recovers, mimicking real photocell persistence. Teletronix LA-2A, Universal Audio LA-3A
Tube Computes a variable-mu ratio tubeMu = 1 + depth × 1.8 where depth = GR/20. Applies extra GR, making the ratio increase as the signal gets louder — classic variable-mu behaviour. Also the slowest attack and release. Vari-Mu, Manley Variable Mu

Step 7 — Apply compression gain + limiter (lines 242–264)

const float compGain = Decibels::decibelsToGain(envelope) * outputLinear;
for (int ch …) {
    const float compressed = buffer.getSample(ch, i) * compGain;
    float out;
    if (limiterOn)
        out = jlimit(-1.0f, 1.0f, tubeSaturate/fetSaturate(compressed, 0.08f));
    else
        // gentle output saturation by mode (adds character)
        out = fetSaturate / tubeSaturate(compressed, 0.06-0.10f);
    buffer.setSample(ch, i, out);
}

When the hard limiter is ON: the signal is saturated and then hard-clipped to ±1.0 (0 dBFS), preventing digital clipping in the DAW. When OFF: a very gentle output saturation (drive 0.06–0.10) adds warmth without clipping.

Step 8 — Parallel mix blend (lines 267–274)

const float wet = mixAmt, dry = 1.0f - mixAmt;
for (ch, i)
    buffer[ch][i] = buffer[ch][i] * wet + dryBuffer[ch][i] * dry;

Parallel compression: blends the fully compressed signal (wet) with the uncompressed original (dry). At 50% mix you get a punchy blend of dynamics. This is the classic "New York compression" trick.

Steps 9–10 — Output oscilloscope + metering (lines 276–285)

Mixes down to mono and pushes to outputWaveform for the OUTPUT oscilloscope. Atomically stores the current block's gainReductionDb (= envelope) and currentInputLevelDb for the GUI widgets.

getStateInformation / setStateInformation (lines 288–300)

timerCallback() — the display update loop

void timerCallback() {
    const int pixW = getWidth() - 2 * kFrameW - kLabelW;
    const int wp   = waveformBuffer.writePos.load(memory_order_acquire);  // acquire fence!

    if (displayWidth != pixW || lastWritePos < 0)
        initialiseDisplayBuffer(pixW);   // first run or resize — full rebuild
    else
        updateDisplayBuffer(pixW, wp);    // normal path — incremental shift
    repaint();
}
Why memory_order_acquire here? The audio thread uses memory_order_relaxed when writing writePos (after all sample data is written). The GUI uses acquire when reading — this creates a happens-before relationship that guarantees the GUI sees all sample data written before the writePos update. Without this, the CPU could reorder reads and you might read a new writePos but old sample data.

initialiseDisplayBuffer(pixW)

Fills all pixW pixel columns from scratch by walking backwards through the ring buffer. Column 0 (left edge) = oldest audio, column pixW−1 (right edge) = newest. For each pixel column, it averages spp (samples-per-pixel) consecutive samples to find the min and max amplitude.

updateDisplayBuffer(pixW, wp)

The incremental (fast) path called on every timer tick:

  1. Calculate how many new samples have arrived since last tick
  2. Convert to pixel columns via pixelAccum (fractional accumulator)
  3. Use memmove() to slide all existing pixel data left by shift columns — O(N) but only 57344/spp bytes
  4. Fill the rightmost shift columns with fresh min/max data from the ring buffer
Why memmove and not a loop? memmove() is a highly optimised C runtime function — on modern CPUs it uses SIMD instructions (SSE/AVX) and is typically 10–20× faster than a manual loop for this operation.

paint() — drawing the waveform

Three drawing passes over the pre-computed dispMin/dispMax arrays:

  1. Filled polygon — traces max values forward then min values backward to form a closed shape, filled with 42% opacity waveform colour
  2. Bright top edge — anti-aliased stroke along the max values at 1.5 px width
  3. Dimmer bottom edge — mirrors the min values, 1.0 px, 55% opacity

For the INPUT display only: draws the threshold line as a red dashed horizontal line (with a subtle red glow background), showing exactly where compression starts.

VuMeter.h / .cpp Analogue-style needle meter with ballistic smoothing

Emulates a vintage VU meter movement. The needle swings right for 0 dB GR (no compression) and left for heavy gain reduction.

timerCallback() — ballistic needle physics (60 Hz)

const float targetAngle = 35.0f + grClamped * (70.0f / 20.0f);
const float alpha = targetAngle < needleAngleDeg ? 0.42f : 0.09f;
needleAngleDeg += (targetAngle - needleAngleDeg) * alpha;
  • targetAngle: maps −20 to 0 dB GR linearly to −35° to +35°
  • alpha = 0.42: fast response when GR is increasing (needle swings left quickly — like a real meter attacking)
  • alpha = 0.09: slow response when GR is decreasing (needle drifts right slowly — like a real meter releasing)
  • This exponential smoothing mimics the inertia of a physical meter movement

paint() — needle drawing

The pivot point is at the bottom-centre of the face area. The needle angle is converted to an (x, y) tip position using:

x = pivX + radius * sin(angleDeg)
y = pivY - radius * cos(angleDeg)

The needle is drawn in three parts: a drop shadow (offset 1.2 px), a dark body, and a red tip (the top 18% of the needle length). A pivot circle is drawn last.

The red LED at the bottom lights up whenever GR exceeds 0.3 dB, with a radial gradient for a realistic illuminated look.

10. GrCurveDisplay — Live Transfer Curve

GrCurveDisplay.h / .cpp Draws the compressor's input→output transfer function in real time

Shows a graph of input dBFS (X axis) vs output dBFS (Y axis) for the current threshold/ratio/knee settings. A moving dot shows exactly where on the curve the signal is operating right now.

computeOutputDb() — the same formula as processBlock

static float computeOutputDb(float inDb, float thresh, float ratio, float knee) {
    const float hk = knee * 0.5f;
    if (knee > 0 && inDb >= thresh - hk && inDb <= thresh + hk)
        return inDb + (inDb - thresh + hk)^2 * (1/ratio - 1) / (2*knee);  // soft knee
    if (inDb > thresh + hk)
        return thresh + (inDb - thresh) / ratio;  // above threshold
    return inDb;  // below threshold — unity gain
}

This is identical to the formula in processBlock() — which is the whole point. If the curve shows a certain amount of reduction at a given input level, that is exactly what the audio is doing.

paint() — drawing the curve

  1. Grid lines at −60, −40, −20, 0 dBFS with axis labels
  2. Threshold vertical line — red dashed vertical at current threshold position
  3. Knee shaded region — dark overlay over the knee transition zone
  4. Compression curve — walks pixel-by-pixel across the plot width, computing output for each input, drawn as a blue line with a 4 px glow pass first
  5. Operating-point dot — reads inputLevelDb from the atomic, computes corresponding output, draws an amber dot with a glow ring
Timer runs at 30 Hz here (vs 120 Hz for oscilloscopes) because the curve only needs to redraw when parameters change or the dot moves — it does not need to scroll.

11. DSP Deep-Dive — Compression Math Explained

11.1 The Fundamental Compressor Equation

Given input level x dBFS and threshold T dBFS:

  • If x ≤ T: output = x (no effect)
  • If x > T: output = T + (x − T) / R
  • Gain reduction GR = output − x = (T + (x − T)/R) − x = (T − x)(1 − 1/R)

Example: T = −20 dBFS, R = 4:1, x = −10 dBFS

  • Output = −20 + (−10 − (−20)) / 4 = −20 + 2.5 = −17.5 dBFS
  • GR = −17.5 − (−10) = −7.5 dB

11.2 Soft Knee

A hard knee means compression starts abruptly at threshold. A soft knee applies a quadratic transition in the region [T − K/2, T + K/2] where K = knee width in dB: 

GR = (x − T + K/2)² × (1/R − 1) / (2K)

This makes the compression onset gradual — the curve "bends" smoothly rather than having a sharp elbow, producing a more transparent sound especially at low ratios.

11.3 Envelope Follower — The One-Pole IIR Filter

The smoothed gain reduction follows this recurrence relation each sample:

envelope[n] = coeff × envelope[n−1] + (1 − coeff) × GR[n]
where coeff = exp(−1 / (τ × sampleRate))  and  τ = time_constant_in_seconds

The coefficient controls how quickly the envelope tracks the target GR:

  • coeff = 0.9999 → extremely slow (long time constant)
  • coeff = 0.90 → fast (short time constant)
  • coeff = 0.0 → instantaneous (no smoothing)

Separate attack and release coefficients allow the compressor to respond quickly to louder signals (GR becoming more negative = compressing harder = attacking) but release slowly (GR returning to 0 = signal quieter = releasing).

11.4 Mode-Specific Envelope Behaviours

VCA (Voltage Controlled Amplifier)

Clean, predictable, transparent. Used on busses and anywhere you want control without colouration. The envelope is a classic one-pole IIR with the user-set attack and release times.

FET (Field-Effect Transistor)

Attack clamped to ≤ 2 ms — extremely fast, catches and controls transients aggressively. Input saturation adds odd- and even-harmonic content. This is what makes drums sound "punchy" and "aggressive". Models the 1176-style compressor circuit.

Optical

Uses a separate opticalState variable (0–1) that represents the brightness of a photocell. The photocell charges quickly (attack) but discharges on a log curve: 

envelope = −opticalState × 20 × (1 + opticalState × 0.5)

The × (1 + opticalState × 0.5) term makes the release programme-dependent: heavy GR takes longer to release than light GR. This is the characteristic of real optical compressors (LA-2A, LA-3A) and makes them sound "musical" — they breathe with the music naturally.

Tube (Variable-Mu)

Computes a variable ratio multiplier: tubeMu = 1 + depth × 1.8 where depth = −GR/20 (0–1 scale). This means the effective ratio increases as the signal gets louder — very heavy transients get more compression than moderate signals. Combined with the slowest attack/release times, this gives the famous "gluing" effect on master bus.
